# 数据库设计暂定基线

状态：本轮数据库设计已由组长确认，形成开发基线；未执行建表、迁移、导入或数据修改。此文是数据库设计材料，不代表整个设计文档或数据库实现已完成。

## 1. 本轮确认

1. 保留12张业务及认证表：user、team、player、team_player、coach、team_coach、venue、football_match、player_match_stat、honor、team_honor、comment。migration为框架辅助表，不用于凑课程业务表数量。
2. 所有录入成功的球队、球员、比赛等业务资料立即公开，不增加草稿、发布状态或发布按钮。留言例外，仍须审核，只有approved公开。管理员user不属于公开资料。
3. football_match只保留match_date_beijing（DATE）作为比赛日期，移除local_match_date及kickoff_utc。场馆timezone一并移除，不进行时区换算。页面及日期筛选均按北京时间日期。
4. 所有业务表移除source_ids/source_page，来源留在资料说明文档；资料说明按实体类型和稳定标识（如球队三字码、比赛编号或内部ID）对应记录，后续修改数据时同步维护。导入前需另行调整旧SQL及JSON转换，不能直接执行原资料包SQL。
5. 复用yii2advanced既有user，保留现有admin及密码，不重建user或migration，不在本设计步骤写库。
6. 由组长先确定数据库方案，组员后续据此编码；常规设计不设三人会签为开工前置。影响其他模块的变更需同步。原分工中的三人数据表设计贡献、共同审核计划与此安排有差异，最终文档应按真实贡献填写，不能虚构成员设计或审核记录。

## 3. 已延续的关系规则

- team→team_player←player；阵容记录保存年份、号码、位置，统计通过team_player关联球员及球队。
- team→team_coach←coach；team→team_honor←honor。
- venue→football_match；比赛双方至少一侧关联库内球队。库外对手只保存名称，对应球队ID可空；两侧为库内时不得相同。修正需求中“两侧均须存在球队记录”与“库外只存名称”的文字冲突，沿用已确认的库外名称方案。
- football_match→player_match_stat←team_player。统计所属年份、球队必须与比赛一致。
- comment三个目标外键恰好一个非空，对象必须存在。reviewed_by引用user.id；只允许指定管理员执行审核。
- 所有关联默认RESTRICT，阻止静默级联删除历史记录。并发和跨表一致性由模型/事务及外键共同保证，不能仅依赖表单。
- 战绩只统计2026、finished、双方比分完整的比赛；胜平负按含加时、不含点球大战的比分判断；不存冗余胜平负汇总表。

## 5. 录入与修改约束

- finished必须同时填写双方非负整数比分；not_started/live/postponed/cancelled双方比分必须均为NULL。不得单独保留一侧比分；已有任意球员统计时，比赛双方ID及名称、赛事年份、状态、比分均锁定，禁止修改（包括改为空）。没有统计时也须遵守比分与状态规则。
- 名称等核心识别字段必填。队徽、球员/教练照片、球队/教练简介及球员出生日期可空。缺图用占位图，出生日期未知不显示年龄。其余字段按上表填写。
- 阵容的球队、球员、年份、号码、位置必填，号码和位置范围沿用底稿。
- player_match_stat仅录入已核实的出场和进球，appeared与goals必填且无代表未知的默认0；assists可空。缺失整条统计记录表示未录入/未核实，不能解释为未出场或0进球。
- appeared=0时goals必须0，assists若已知必须0；appeared=1时goals可为0。进球不超过该球员所在球队本场比分，统计仅覆盖已收录且已核实场次。

- 同届球员仅归属一队；每队同届仅一名主教练。team_coach.role固定head_coach；首版年份固定2026，不增加历届赛事维护页面。
- 球员统计只允许关联finished比赛；阵容年份和参赛球队须匹配。已有统计的阵容记录，其球队/球员/年份也不得直接修改，以免绕过比赛锁定。
- 统计存在时允许编辑比赛日期、阶段、场地等未锁定信息，仍须基本校验。球队资料改名不批量重写已锁定比赛名称快照；比赛详情可保留比赛录入时名称。
- 无需锁定永久记录：先按后台删除规则删除该场全部球员统计后才可修改受锁字段，不能由修改比赛动作自动删除统计。任何现有统计行（包括未出场记录）均触发锁定。
- 仅允许物理删除无引用的业务记录；有关联则拒绝并说明依赖，不增加停用/逻辑删除字段，不静默级联删除。球队、球员、比赛如被留言引用，即使留言已软删除，也不能直接删除目标。
- comment仍为pending→approved/rejected、approved→deleted；rejected/deleted终态，无恢复或物理删除。pending的审核人/时间为NULL，审核和软删除由服务端记录当前管理员及北京时间；不得由访客赋值。
- before/after审核修改由事务和条件更新保证合法状态流转；当前Comment骨架尚不承担后台审核实现。
- 比赛阶段沿用固定枚举：group、round_of_32、round_of_16、quarter_final、semi_final、third_place、final；页面显示中文，旧数据导入前须映射核对，不直接假定旧值相同。
- 数字边界：号码1—26；位置GK/DF/MF/FW；appeared/after_extra_time为0或1；比分、进球、已知助攻均为非负整数；官方编号为正整数。出生日期有效且不晚于当天；荣誉year为有效正整数年份，不混入本届战绩。

## 6. 索引与外键

所有外键均采用ON DELETE RESTRICT / ON UPDATE RESTRICT，不存在关系时必须存NULL而非0。跨表条件不能只靠FK或CHECK，需模型校验与事务；实际写入迁移/SQL时按本机MariaDB兼容语法验证。

| 表 | 主键以外的唯一键 | 其他索引建议 |
| --- | --- | --- |
| user | 复用username、email、password_reset_token | 保持现状 |
| team | fifa_code | name_zh（普通索引，非唯一） |
| player | 无 | name_zh |
| team_player | (player_id,tournament_year)；(team_id,tournament_year,shirt_number) | 唯一键已覆盖两种外键前缀，无需重复索引 |
| coach | 无 | name_zh |
| team_coach | (team_id,tournament_year) | coach_id |
| venue | 无 | 无额外业务索引 |
| football_match | (tournament_year,fifa_match_number) | venue_id；(home_team_id,tournament_year,status)；(away_team_id,tournament_year,status)；match_date_beijing |
| player_match_stat | (match_id,team_player_id) | team_player_id |
| honor | 无 | 无额外业务索引 |

同名球员/教练/场地不强行加名称唯一约束；不能以姓名作为主外键。精确包含查询未必利用普通名称索引，不承诺任意模糊查询均有索引加速。

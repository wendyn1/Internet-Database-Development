# 2026世界杯球队信息系统三人分工方案

编制日期：2026年10月28日  
适用范围：当前《需求文档.md》及课程课件规定的数据库、代码、文档、演示与交付任务。  
人员代称：A为组长（你），B为组员一，C为组员二；定稿时替换为真实姓名、学号。  
执行方案：按业务模块负责，数据库与代码分别统筹；三人共同参与数据表设计、MVC开发和全部成果审核。

## 1. 分工依据与共同原则

1. 工作量包含需求访谈、需求文档、分工规划、数据表设计、代码、资料整理、文档、测试、集成、部署和演示。A已完成的需求确认及文档工作、此次分工工作计入总量，不在其基础上再平均追加全部开发任务。
2. 每人必须实际编写至少一个Model、一个Controller、一个View文件，并保留本人Git提交。仅运行Gii生成代码、署名、审核或编写SQL，不能替代实际MVC开发贡献。
3. 每人实际参与数据表设计，明确自己的字段、键、关系和约束贡献；统筹数据库的人负责统一，不代替其他人的设计责任。
4. 文档主笔负责组织成稿，其他两人提供自己的模块内容与证据；最终每份文档、每个代码模块及公共代码均由三人共同审阅。作者自检，另外两人交叉审核，记录修改结果后才纳入交付版。
5. 以业务模块划分开发边界，同一人尽量负责本模块前后台、模型和验证，避免按“一个人模型、一个人控制器、一个人页面”拆分造成连续等待。
6. 首轮冻结字段、接口和共享页面约定；后续各自使用约定的样本数据并行开发。跨模块变更必须同步，不能自行修改公共约定。
7. 工作量以相对点数估算，不将表数、文件数或文档页数机械等同于工作量。本方案总计300点，三人各100点，约各占33.3%；实施时依据实际投入与缺陷修复量调整并如实记录。

## 3. 公共数据与代码约定

### 3.1 十二张表的建议命名

| 表 | 内容 |
| --- | --- |
| `user` | 复用Yii2用户模型，后台管理员身份与认证 |
| `team` | 球队基本信息 |
| `player` | 球员基本资料 |
| `team_player` | 本届赛事阵容、号码、位置 |

| `team_coach` | 球队执教关系 |
| `venue` | 比赛场地 |
| `football_match` | 比赛日期、阶段、双方、状态、比分 |
| `player_match_stat` | 球员出场、进球等统计 |
| `honor` | 荣誉定义 |
| `team_honor` | 球队获得荣誉的记录 |

以上为分工与接口讨论用的建议表名，最终字段及约束由设计评审确定。下载文件可使用服务端白名单清单，不为凑表数量增加下载表。

### 3.2 首轮必须解决的需求歧义

- 库外对手：按当前需求只展示其名称。建议比赛的主客队关联允许一侧为空，同时保存对应名称，至少一侧为库内球队；库内球队必须引用ID。三人评审确定约束，禁止为库外对手强行补完整阵容。统计只按库内球队ID聚合；同队对阵仍须校验。
- 比赛状态：页面可仅显示日期与比分，但状态和阶段仍是筛选及统计所需字段，应保留在数据和后台维护中。
- 球员统计：当前功能正文以出场、进球为基础；候选表中出现的助攻不作为新增必做页面，设计时统一口径。
- 初始球队与数据量：六支重点球队及具体样本由三人共同选定，记录来源。本文不额外增加新闻、完整晋级、事件直播等已不在当前需求中的功能。

### 3.3 提前冻结的接口

| 接口或数据约定 | 内容 | 使用方 |
| --- | --- | --- |
| 球队选择列表 | 球队ID、中文名；不返回未经约定的临时字段 | 比赛、对比、阵容维护 |
| 球员所属关系 | 球员ID、球队ID、位置、号码及本届赛事归属 | 球员详情、比赛统计校验 |
| 比赛统计服务 | 输入球队ID，输出有效场次、胜平负、进失球；排除未结束或比分不全记录 | 球队详情、对比、饼图 |
| 留言组件 | 输入目标类型与ID，展示通过审核的留言和提交表单 | 球队、球员、比赛详情 |
| 公共后台权限 | 所有后台控制器共用身份检查，禁止只隐藏菜单 | 全部后台模块 |
| 下载清单 | 文件显示名、类型及服务端受控路径；URL只接受清单标识 | 作业下载页面 |

由各接口负责人提供最小样本和调用示例，其他成员不必等待真实页面或完整数据。接口冻结后，新增字段尽量保持向后兼容；破坏性修改先更新设计说明、看板和受影响成员。

## 4. 按业务模块负责，数据库与代码分别统筹

特点：B统筹数据库，C统筹业务代码集成，A负责前期需求、中期进度和后期汇总；三人仍独立设计自己模块的表并开发完整MVC。它保留集中统筹的效率，同时满足每人实际编写MVC的硬要求。

| C 组员二 | 比赛和统计模块；代码集成及部署统筹 | `venue`、`football_match`、`player_match_stat` | 统一共享接口和后台接入方式，负责Windows初始化脚本、联调与运行问题定位 |

## 6. 三人共同审核与贡献留证

### 6.3 最终共同核验

三人共同核对12张表、三人的MVC链路、全部文档与代码，并共同走通：访客查询→球队/球员/比赛详情→对比与饼图→留言提交→后台审核→前台展示→数据维护→统计更新→团队及个人作业下载→初始化还原。

录屏建议由A组织提纲并合并录制，B演示基础资料与数据库，C演示比赛、图表与部署；三人各自讲解本人模块。其准备计入审核与演示额度，不另叠加一整轮工作。

## 7. 编码与交付统一规范

### 7.1 命名及注释头

- 表、字段使用小写下划线，如 `team_player`、`player_id`；主键、外键和时间字段统一约定。
- PHP类名使用大驼峰，如 `FootballMatch`；控制器以 `Controller` 结尾；方法和变量使用小驼峰；控制器action遵循Yii2路由约定。
- 视图目录和路由采用Yii2惯例，如 `team-player`；视图文件使用 `index.php`、`view.php`、`_form.php`。不为了统一外观改坏框架约定。
- 文件使用UTF-8，代码缩进统一4空格，复用框架校验与查询能力，不拼接用户输入构造SQL。
- 本项目交付的PHP文件包括视图、配置、控制器、模型、迁移和自编脚本，均检查注释头；第三方依赖不批量篡改，模板与生成文件需保留原版权及许可说明。

```php
<?php
/**
 * 项目：2026世界杯球队信息系统
 * 文件职责：球队比赛信息查询与详情展示
 * 作者：姓名（学号）
 * 创建日期：YYYY-MM-DD
 * 主要修改者：姓名（学号）；具体修改记录见Git
 */
```

注释头署名必须对应真实贡献；共同审核不等于共同编写，不在所有文件中统一写三人的名字代替贡献记录。

### 7.2 最终目录与命名

```text
仓库根目录/
└─ data/
   ├─ install.sql
   ├─ team/
   │  ├─ advanced/                    # 当前Yii2代码
   │  └─ 文档/
   │     ├─ 需求文档/                 # Markdown源稿、分工方案、提交PDF
   │     ├─ 设计文档/
   │     ├─ 实现文档/
   │     ├─ 用户手册/
   │     ├─ 部署文档/
   │     ├─ 项目展示PPT/
   │     └─ 录屏讲解/                 # 按最新课程要求准备
   └─ personal/
      ├─ 学号A_姓名A/                 # 本人的作业1、2、3
      ├─ 学号B_姓名B/
      └─ 学号C_姓名C/
```

六项提交文件按课件命名，例如 `队名_需求文档(学号A_学号B_学号C).pdf`，其他文档相应替换类型；展示稿使用PPT/PPTX或PDF按课程允许格式提交。现有Markdown作为源稿保留，不直接把Markdown或旧PPT占位文件当作已完成提交版。

SQL最终落点是仓库 `data/install.sql`，不是 `data/team/data/install.sql`。当前工作目录为 `data/team`，因此SQL和个人作业目录均在上一级；实施到相关任务时由负责成员按实际写权限操作，本分工文件不表示这些文件已生成。

### 7.3 下载入口要求

前台导航提供“课程作业下载”，分为团队成果和三位成员个人作业。后台或服务端清单维护文件显示名与受控路径；不允许访客任意传路径读取磁盘。没有提交版时显示“待上传”，不放无效链接；最终验收时全部必需文件须可下载，且文件内容与名称一致。

建议通过Yii2下载控制器发送文件，不把整个 `data` 目录直接暴露为静态目录。A实现下载逻辑，每人整理本人个人作业及负责的团队材料，另外两人分别核验链接和内容。
